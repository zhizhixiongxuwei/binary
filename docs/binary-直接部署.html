binary-deploy 跨平台离线部署操作说明

同一交付目录支持 Windows、Linux 和 macOS 主机。Windows 使用 PowerShell 脚本，Linux/macOS 使用 Shell 脚本；三种主机最终运行的都是交付包内固定的 Linux/AMD64 容器。

交付文档 V1.0Windows：PowerShell + Docker DesktopLinux/macOS：Shell9 个运行服务数据统一位于 data/
操作顺序： 选择系统 → 封存验真 → 导入镜像 → 配置 → 启动 → 业务验收 → 日常运维

2. 先按现场操作系统选择脚本

Windows 10/11 x64

  • 安装 Docker Desktop，启用 WSL2 backend。
  • 必须使用 Linux containers，不能切换到 Windows containers。
  • 使用 Windows PowerShell 5.1 或 PowerShell 7。
  • 建议放到 C:\BinaryScan\binary-deploy，不要放 OneDrive、网络盘或压缩包内部。
cd C:\BinaryScan\binary-deploy
docker info --format '{{.OSType}}/{{.Architecture}}'
$PSVersionTable.PSVersion

Linux x86_64

  • Docker Engine + Compose v2。
  • 目标必须是 AMD64。
  • 初始化、检查和重置建议统一使用 sudo。
  • 当前账号若直接操作 Docker，需具备 Docker daemon 权限。
cd /opt/binary-deploy
docker version
docker compose version
uname -m

macOS

  • 安装并启动 Docker Desktop。
  • Intel Mac 可直接运行 AMD64 镜像。
  • Apple Silicon 通过模拟运行，仅建议制备和现场演示，不作为高负载生产服务器。
  • 使用 Terminal 执行 *.sh。
cd /交付路径/binary-deploy
docker version
docker compose version
uname -m
Windows 最重要的检查：Docker Desktop 托盘菜单如果显示“Switch to Linux containers”，说明当前仍在 Windows containers 模式，必须先切换；本交付不包含 Windows 容器镜像。
现场 Docker 需要支持 Compose v2 的 up --wait 与 --pull never。交付脚本会检查 Docker/Compose 是否存在，但正式验收前仍应在目标机实际执行 doctor 和一次完整启动，不能只根据版本号推断兼容。

3. 封存验真：每个系统执行什么

Windows PowerShell

cd C:\BinaryScan\binary-deploy
Set-ExecutionPolicy -Scope Process Bypass -Force
Get-ChildItem .\*.ps1 | Unblock-File
.\verify.ps1 package
(Get-FileHash .\manifests\package.sha256 -Algorithm SHA256).Hash

Linux

cd /opt/binary-deploy
chmod +x ./*.sh
./verify.sh package
sha256sum manifests/package.sha256

macOS

cd /交付路径/binary-deploy
chmod +x ./*.sh
./verify.sh package
shasum -a 256 manifests/package.sha256
必须把 manifests/package.sha256 自身的 SHA-256 与用户封存日保存在交付目录之外的纸质、签字文件或可信介质记录比较。只检查目录内部文件不能建立最终可信根。脚本验证清单内文件内容，不拒绝目录中后来增加的额外文件；验收时不要运行来源不明的附加脚本。

4. 离线导入九个运行镜像

Windows

.\load-images.ps1
docker image ls

Linux

sudo ./load-images.sh
sudo docker image ls

macOS

./load-images.sh
docker image ls

导入脚本先使用 SHA-256 校验每个 *.tar，校验失败不会执行 docker load。全过程不需要访问镜像仓库。

5. 配置访问地址和管理员账号

默认只允许从服务器本机访问 http://localhost:8080。需要单位内网访问时，必须在完成封存验真后修改 .env：

APP_BIND_IP=0.0.0.0
PUBLIC_BASE_URL=http://服务器固定内网IP:8080
APP_ALLOWED_ORIGINS=http://服务器固定内网IP:8080

Windows 查看/编辑

notepad .env
Select-String -Path .env -Pattern '^INITIAL_ADMIN_'

Linux 查看

sudo grep '^INITIAL_ADMIN_' .env

macOS 查看

grep '^INITIAL_ADMIN_' .env
每套交付目录由制备脚本分别生成随机管理员密码，用户名默认 admin，实际密码以各自 .env 为准。初始账号只在空数据库首次启动时创建；普通重启后修改 INITIAL_ADMIN_* 不会覆盖数据库中的现有密码，只有清空数据库后才会重新引导。
修改 .env 属于封存验真后的受控现场配置变更，因为 .env 本身在 package 清单内，修改后再次执行原始 package 验真会失败，这是预期结果。应保留一份只读原始包，并记录配置变更，不能把修改后的目录继续宣称为原始封存包。
不要把 BINARY_DATA_ROOT 改成盘符根目录、用户目录或其他路径。脚本固定要求 ./data，并拒绝把符号链接或 Windows junction 当作数据根目录。

8. 当前版本业务验收主线

  1. 服务端按内容而不只是扩展名识别 PE（EXE/DLL/SYS）、ELF、Mach-O、CLASS、JAR、WAR、EAR、DEX、APK、PYC，ZIP、7Z、RAR、TAR、GZIP、XZ、DEB、RPM、ISO 9660、EXT4，以及 Docker Save/OCI Layout TAR；上传完成后再选择“二进制”“归档”或“容器/映像”分析模式。.img 只是后缀，不能单独确定内部格式。
  2. 二进制模式按实际识别结果进入 Ghidra、JVM 或 PYC 反编译，再手动启动 C、Java 或 Python 源码检查；源码、行列定位和 finding 均写入 data/。在线任务页的 Monaco Editor 可以读取持久化源码；下载后的离线 HTML 报告只展示路径、行列和代码片段，不提供依赖系统地址的“在源码中打开”链接。
  3. 选择归档模式后自动排队一次只读解析；ZIP/TAR 内的嵌套归档不递归，.tar.gz/.tar.xz 的包装与 TAR 载荷算同一逻辑层。ISO 9660 和 EXT4 不执行宿主机 mount，而是只读遍历镜像目录树。解析后由用户选择符合条件的成员，每批最多 10 个，手动批量创建二进制子任务；各子任务再独立反编译、检查并导出 JSON、HTML 或 DOCX 报告。
  4. 从左侧“归档批次”展开对应批次，选择格式生成总报告 ZIP；每种所选格式取各子任务最新 ready 报告，可选包含已收录任务的 ready 反编译源码。manifest.json 完整记录缺失格式、运行和省略原因；index.html 提供已包含/已省略任务及报告链接的可读摘要。
  5. 容器/映像模式由用户手动启动 Trivy。只有识别为 Docker Save TAR 或 OCI Layout TAR 的内容可检测；二者改名 .img 后仍按内部结构识别。ISO、EXT4、普通 TAR、原始/分区磁盘 IMG 或其他不适用内容应明确显示“不适用/无结果”，不得伪造漏洞。
单任务报告只允许选择同一任务中已经终态的运行，最多 100 个；0 finding 也可生成报告。finding 超过 50,000 条时报告会明确标记截断。总报告不会自动替子任务启动反编译、checker 或单任务报告；至少要有一份符合所选格式的 ready 报告，报告及可选源码的声明未压缩总量上限为 4 GiB。
Trivy 时效边界：结果基于 scanner 镜像内封存的 Trivy 离线漏洞库快照，现场不会联网更新，只反映该快照已知漏洞。更新漏洞库必须重新制备、验证并封存 scanner 镜像。

10. 清空全部数据并重新启动

不可恢复：会删除数据库、账号、上传文件、二进制、反编译源码、finding、单任务报告、归档总报告和工作目录。日常重启不要使用。

Windows

.\manage.ps1 reset -Yes

Linux

sudo ./manage.sh reset --yes

macOS

./manage.sh reset --yes

Windows 脚本要求 -Yes，Shell 脚本要求 --yes。两者都会验证目标严格等于当前交付目录的 data、不是符号链接/junction，并且哨兵与 Compose 项目名一致。

11. Windows 常见问题与跨平台排查

  • PowerShell 提示禁止运行脚本：执行 Set-ExecutionPolicy -Scope Process Bypass -Force，只影响当前窗口；必要时执行 Get-ChildItem .\*.ps1 | Unblock-File。
  • 提示 Docker Desktop must use Linux containers：在 Docker Desktop 菜单切换到 Linux containers，并确认 WSL2 engine 已启动。
  • Windows 文件共享或挂载失败：把交付目录移动到本机 NTFS 盘的短路径，例如 C:\BinaryScan，不要使用网络盘、OneDrive 按需文件或压缩包内路径。
  • 平台不匹配：交付镜像是 linux/amd64；Windows ARM 设备不作为正式验证目标。
  • 镜像缺失：Windows 重新执行 .\load-images.ps1；Linux/macOS 重新执行 ./load-images.sh。
  • 端口占用：完成封存验真后同步修改 APP_PORT、PUBLIC_BASE_URL 和 APP_ALLOWED_ORIGINS；若开放内网访问还要核对 APP_BIND_IP。三处地址不一致会导致浏览器 Origin 校验或写操作失败。
