binary-demo 跨平台源码验真与现场修改说明

Windows、Linux、macOS 均可完成“校验封存 → 导入镜像 → 断网编译原版 → 启动九服务 → 现场小改 → 再编译 → 替换 App → 对比证据”。Windows 全程使用交付包内 PowerShell 脚本。

Windows：*.ps1Linux/macOS：*.sh构建网络：none封存范围：backend + frontend + Dockerfile
验证主线： 选择系统 → 校验封存 → 导入镜像 → 编译原版 → 启动 → 现场修改 → 再次编译 → 证据对比
1可信哈希确认源代码未变
2断网构建生成 App 镜像
3九服务启动证明可运行
4现场修改 UI 或 API
5重建替换并观察变化

1. 这套验证能证明什么

  • 验证日的 backend、frontend、App Dockerfile 与封存日内容一致。
  • 给定封存的基础镜像和依赖缓存，Windows 或类 Unix 主机都能在 --network=none 下构建 App。
  • 现场新构建的 App 能与预置 MySQL、scanner、三个反编译器和三个 checker 共同运行。
  • 修改 App 范围的小功能后，源码摘要和 App 镜像 ID 变化，其他八个运行镜像保持不变。
该流程证明输入一致、可离线构建、可运行和可修改，不承诺不同 Docker/文件系统环境生成字节完全相同的镜像 ID。最终镜像标签会记录源码摘要和依赖锁摘要。

3. 现场操作系统准备

Windows 10/11 x64

  • Docker Desktop 使用 WSL2 backend 和 Linux containers。
  • Windows PowerShell 5.1 或 PowerShell 7。
  • 建议路径 C:\BinaryScan\binary-demo。
  • 不要放到 OneDrive、网络盘、U 盘直接运行或压缩包内部。
  • Docker Desktop 建议分配至少 16GB，原生反编译演示建议 24GB。
cd C:\BinaryScan\binary-demo
docker info --format '{{.OSType}}/{{.Architecture}}'
$PSVersionTable.PSVersion
Set-ExecutionPolicy -Scope Process Bypass -Force
Get-ChildItem .\*.ps1 | Unblock-File

Linux x86_64

  • Docker Engine + Compose v2。
  • 目标 CPU 必须是 AMD64。
  • 建议统一用 sudo 执行镜像导入和 manage 脚本。
  • 源码修改可使用普通用户，避免把源文件改成 root 所有。
cd /opt/binary-demo
chmod +x ./*.sh
docker version
docker compose version
uname -m

macOS

  • Docker Desktop 已启动。
  • Intel Mac 可直接运行；Apple Silicon 使用 AMD64 模拟。
  • Apple Silicon 适合验证演示，不建议承担生产反编译负载。
  • 通过 Terminal 运行 *.sh。
cd /交付路径/binary-demo
chmod +x ./*.sh
docker version
docker compose version
uname -m
Windows 必须是 Linux containers：如果 Docker Desktop 菜单显示“Switch to Linux containers”，说明当前模式不正确。切换完成并等待 Docker Desktop 重新启动后再继续。不要在同一次验证中混用 PowerShell 脚本与 WSL 内的 Shell 脚本。

4. 阶段一：验证完整包和 App 源代码

Windows PowerShell

cd C:\BinaryScan\binary-demo
.\verify.ps1 package
.\verify.ps1 source
(Get-FileHash .\manifests\package.sha256 -Algorithm SHA256).Hash
(Get-FileHash .\manifests\source.sha256 -Algorithm SHA256).Hash

Linux

cd /opt/binary-demo
./verify.sh package
./verify.sh source
sha256sum manifests/package.sha256
sha256sum manifests/source.sha256

macOS

cd /交付路径/binary-demo
./verify.sh package
./verify.sh source
shasum -a 256 manifests/package.sha256
shasum -a 256 manifests/source.sha256

两个清单文件自身的 SHA-256 必须与用户封存日在交付目录之外记录的可信值一致。建议记录设备、操作系统、操作人、时间、manifests/source-git.txt 和完整命令输出。

6. 阶段三：从原始封存源码离线编译

Windows

.\build-app.ps1
docker image inspect binaryscan/app:0.1.0-dev --format '{{json .Config.Labels}}'

Linux

sudo ./build-app.sh
sudo docker image inspect binaryscan/app:0.1.0-dev --format '{{json .Config.Labels}}'

macOS

./build-app.sh
docker image inspect binaryscan/app:0.1.0-dev --format '{{json .Config.Labels}}'

Windows 和 Shell 两版构建脚本使用相同文件排序、相同 LF 清单格式和相同 SHA-256 算法，因此同一份源码与依赖锁会得到相同的源码摘要和依赖摘要。两版都固定：

  • --platform linux/amd64
  • --network=none
  • --pull=false
  • 源码摘要与依赖锁摘要写入最终 App 镜像标签
  • 构建证据写入 build-output/

8. 阶段五：现场添加小功能

先复制一份已经验真的工作目录，原始副本保持只读。Windows 可使用 VS Code 打开 C:\BinaryScan\binary-demo\app；Linux/macOS 打开对应 app/。

推荐修改位置原因
增加“现场验证版本”文字、说明卡片或本地按钮app/frontend/src/肉眼可见，不涉及数据库和其他镜像。
增加只读 App API 或版本响应字段app/backend/internal/app/可证明后端修改，但不能改变 worker/checker 协议。
现场小改不要新增 npm/Go 依赖、数据库迁移、任务表字段，也不要修改 scanner、反编译 worker 或 checker 协议。离线依赖镜像只覆盖封存时的锁文件。

9. 阶段六：再次编译并应用修改

Windows

.\build-app.ps1
.\manage.ps1 restart-app
.\manage.ps1 status
.\verify.ps1 source

Linux

sudo ./build-app.sh
sudo ./manage.sh restart-app
sudo ./manage.sh status
./verify.sh source

macOS

./build-app.sh
./manage.sh restart-app
./manage.sh status
./verify.sh source

restart-app 只强制替换 App 容器，不重建其他八个服务，也不删除数据。修改后执行 source 验真应失败，这是预期证据；原始只读副本仍应继续通过。

11. 离线依赖镜像的作用

断网时无法执行在线 npm ci 和 go mod download，所以 images/build/ 包含由四个锁文件制备的 app-build-deps 镜像。它不包含 BinaryScan 业务源代码，并带有依赖锁组合摘要。Windows 与 Shell 构建脚本都会先比较该标签，锁文件变化时拒绝继续。

12. 能力边界

  • 可证明 frontend、App HTTP API、App 参数校验、查询和展示类修改。
  • app/backend 中也有 worker 共享包，但 App Dockerfile 只编译 cmd/app。
  • scanner、三个 checker、三个反编译器仍由预构建镜像提供，不属于本次源代码封存范围。
  • 如果用户要求证明这些引擎也可修改，需要扩大源代码、Dockerfile 和依赖封存范围。

13. 停止与清空验证数据

行为WindowsLinuxmacOS
停止并保留容器/数据.\manage.ps1 stopsudo ./manage.sh stop./manage.sh stop
移除容器并保留数据.\manage.ps1 downsudo ./manage.sh down./manage.sh down
永久清空 data 并重启.\manage.ps1 reset -Yessudo ./manage.sh reset --yes./manage.sh reset --yes
reset 永久删除数据库、上传文件、二进制、反编译源码、finding 和报告，但不会删除 app/、镜像归档或 build-output/。Windows 必须写 -Yes，Shell 必须写 --yes。

14. Windows 现场常见问题

  • 脚本被策略阻止：Set-ExecutionPolicy -Scope Process Bypass -Force，只影响当前 PowerShell 窗口；下载文件可用 Get-ChildItem .\*.ps1 | Unblock-File。
  • Docker 处于 Windows containers：切换到 Linux containers 并确认 WSL2 engine 已运行。
  • 挂载失败或数据库启动失败：把目录放在本机 NTFS 短路径，退出 OneDrive/网络盘，确认 Docker Desktop 可访问该盘。
  • PowerShell 与 WSL 输出路径混乱：推荐整个验证只用 PowerShell 和 *.ps1；若选择 WSL，则全程改用 *.sh，不要交叉使用。
  • Windows ARM：不是正式支持目标；本交付锁定 linux/amd64。
