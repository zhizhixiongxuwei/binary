binary-demo 源代码验真与现场修改验证说明

本流程用同一套封存源代码完成“验真、断网编译、启动、现场小改、再次编译、替换 App、观察变化”的证据闭环。

封存范围：backend + frontend + App Dockerfile离线构建App 可修改其他引擎镜像不变
验证主线： 校验封存 → 导入镜像 → 编译原版 → 启动验证 → 现场修改 → 再次编译 → 核对证据
1可信哈希确认源代码未变
2断网构建生成 App 镜像
3九服务启动证明可运行
4现场改 UI 或 API
5重建替换后观察变化

1. 这套验证能证明什么

  • 验证日拿到的 App 源代码与封存日的文件内容一致。
  • 给定封存的编译基础镜像和依赖缓存，源代码能在禁止构建网络的条件下编译为新的 App 镜像。
  • 新构建的 App 可以与预置的 MySQL、scanner、三个反编译器和三个 checker 共同启动。
  • 修改 backend 或 frontend 中属于 App 的小功能后，能再次编译、替换 App 容器并观察到变化。
这不是“字节级可复现构建”承诺。Docker/编译器元数据可能让同一源代码的镜像 ID 不完全相同；本流程验证的是输入一致、可离线构建、可运行和可修改，并用源代码摘要标签建立对应关系。

2. binary-demo 目录组成

路径性质用途
app/backend/封存输入Go 后端源代码；现场只构建 cmd/app。
app/frontend/封存输入Vue 前端和 Monaco Editor 相关页面代码。
app/Dockerfile封存输入从离线依赖构建前端、嵌入 Go App 并生成最终镜像。
app/.dockerignore封存输入限制构建上下文，排除本地产物。
images/runtime/封存工具九个可直接启动的运行镜像。
images/build/封存工具Go、Node、App runtime 和由锁文件生成的离线依赖缓存镜像。
build-app.sh构建程序核对依赖锁摘要，使用 --network=none 编译 App，记录构建证据。
build-output/可变输出每次构建的源码明细、依赖明细和镜像证据，不属于初始封存清单。
data/可变输出数据库、上传、反编译源码、finding、报告和工作目录，不属于初始封存清单。
manifests/封存证据包清单、App 源码清单、Git 提交和镜像 ID。

3. 阶段一：验证封存一致性

用户应先将整个目录复制到验证工作区，保留原始封存介质只读。进入尚未修改的副本：

cd /验证工作区/binary-demo
./verify.sh package
./verify.sh source

package 校验初始交付文件；source 单独校验 app/ 下的 backend、frontend、Dockerfile 和构建忽略文件。再比较可信根：

sha256sum manifests/package.sha256
sha256sum manifests/source.sha256

上述两个值必须和封存日由用户保存在交付目录之外的签字记录一致。macOS 可将 sha256sum 换成 shasum -a 256。

建议现场记录验证时间、设备、操作人、Git 提交（见 manifests/source-git.txt）、两项可信根和命令输出，并由双方签字。

4. 阶段二：导入运行与构建镜像

./load-images.sh

该命令同时导入九个运行镜像和四个 App 构建输入镜像。每个镜像归档都会先做 SHA-256 校验。镜像清单位于：

cat manifests/runtime-images.txt
cat manifests/build-images.txt

为证明构建不依赖外网，可在导入完成后断开网络，或由验证方在隔离网络中继续执行。

5. 阶段三：从原始封存源代码离线编译

./build-app.sh

脚本执行以下约束：

  1. 确认 Go、Node、运行时和离线依赖镜像均已导入。
  2. 重新计算四个依赖锁文件的组合 SHA-256，并与离线依赖镜像标签比较。
  3. 计算整个 app/ 源码树摘要。
  4. 调用 Docker Build，固定 linux/amd64、--pull=false、--network=none。
  5. 把源码摘要和依赖锁摘要写入最终 App 镜像标签。
  6. 在 build-output/ 写入本次源码明细和构建证据。

检查镜像中的源码对应关系：

docker image inspect binaryscan/app:0.1.0-dev --format '{{json .Config.Labels}}'

6. 阶段四：初始化并启动完整系统

sudo ./manage.sh init
sudo ./manage.sh doctor
sudo ./manage.sh start
./manage.sh status

默认从本机访问 http://localhost:8080，随机管理员密码记录在权限为 0600 的 .env：

grep '^INITIAL_ADMIN_' .env

建议完成下列最小冒烟验证：

  • 登录后台并打开首页。
  • 上传一个受支持的二进制样本，确认原文件持久化。
  • 触发对应反编译，确认源码树和 Monaco Editor 可读取源码。
  • 触发对应 checker，确认 finding 能定位到反编译源码。
  • 上传容器镜像 TAR 后手动触发 Trivy，确认报告可查看。

7. 阶段五：现场添加一个小功能

应先复制工作区，再修改副本，保留刚才通过验真的原始副本。推荐选择不增加依赖、不改数据库结构、不改 worker 协议的小功能。

推荐方案 A：前端可视变化

在 app/frontend/src/ 的现有页面增加“现场验证版本”文字、一个说明卡片或一个本地交互按钮。优点是肉眼可见且不涉及数据库。

推荐方案 B：App API 小功能

在 app/backend/internal/app/ 增加一个只读 HTTP 接口或在现有健康/版本响应中增加验证字段，并由前端显示。不得改变 scanner/checker 请求协议。

不要把以下内容作为 App-only 演示：新增 npm/Go 依赖、增加数据库迁移、修改 scanner/反编译 worker、修改 checker 协议、修改任务表结构。它们需要扩展封存范围或重新构建其他镜像，超出本证明边界。

8. 阶段六：重新编译并应用修改

./build-app.sh
./manage.sh restart-app
./manage.sh status

restart-app 使用新镜像强制重建 App 容器，不重建 MySQL、scanner、反编译器和 checker，不删除任何数据。刷新浏览器后应观察到现场增加的功能。

此时执行 ./verify.sh source 应失败，这是预期结果：它证明工作副本已经偏离原始封存源代码。原始只读副本仍应继续通过验真。

9. 阶段七：对比两次构建证据

ls -1 build-output/app-build-*.txt
cat build-output/app-build-*.txt
docker image inspect binaryscan/app:0.1.0-dev --format 'id={{.Id}} source={{index .Config.Labels "com.binaryscan.source-sha256"}}'

现场记录至少应包含：

证据原始构建修改后构建
源码树 SHA-256应与原始源码对应应变化
依赖锁 SHA-256固定应保持相同
App 镜像 ID记录通常变化
构建网络nonenone
其他八个运行镜像 ID记录于清单保持不变
页面/API 行为无现场功能可观察到新增功能

10. 为什么还需要离线依赖镜像

只有 backend/frontend 源码和 Go/Node 基础镜像，断网时无法执行 go mod download 和 npm ci。因此交付包把锁文件对应的 Go module cache 与 node_modules 封装成独立的 app-build-deps 镜像。

  • 依赖镜像不包含 BinaryScan 业务源代码。
  • 它带有四个锁文件的组合摘要标签。
  • 构建脚本先比较摘要，锁文件被修改时会拒绝继续。
  • 真正的前端打包和 Go 编译仍在验证现场从 app/ 执行。

11. 必须对用户说明的能力边界

app/backend 代码树中也包含 scanner 和反编译 worker 的共享包，但本交付的 Dockerfile 只编译 cmd/app。因此：

  • 前端、App HTTP API、App 参数校验、查询与页面展示类修改可以通过本流程证明。
  • 修改共享数据库代码可能让 App 与预构建 worker 行为不一致，应避免作为现场小改。
  • scanner、三个 checker、三个反编译器的内部实现没有作为此次源代码封存范围提供，现场仍使用预构建镜像。
  • 如果用户要求证明扫描引擎或反编译引擎也能修改，必须另行扩大源代码、依赖和 Dockerfile 的封存范围。

12. 清理验证数据

普通停止不会删除数据：

./manage.sh stop
./manage.sh down

确需恢复到空数据库并自动重启时：

sudo ./manage.sh reset --yes
该命令永久删除当前 binary-demo/data/ 中的数据库、上传、二进制、反编译源码、finding 和报告。它不会删除 app/、镜像归档或 build-output/。
