binary-deploy 离线部署操作说明

适用于直接使用已打包九个运行镜像进行交付、导入、启动、停止、状态检查和清空数据后重新初始化的场景。

目标平台：linux/amd64运行服务：9 个运行时不拉取镜像数据统一位于 data/
推荐顺序： 封存验真 → 导入镜像 → 检查配置 → 初始化并启动 → 日常运维

1. 交付内容与适用范围

路径用途
images/runtime/MySQL、App、scanner、三个反编译器、三个 checker 的离线 Docker 镜像归档及各自 SHA-256。
.envCompose 项目名、镜像名、账号密码、端口、并发和资源限制。权限为 0600。
docker-compose.yml九服务运行拓扑、健康检查、网络隔离、只读容器和数据挂载。
load-images.sh先校验镜像 TAR 的 SHA-256，再逐个执行 Docker 导入。
manage.sh初始化、检查、启停、更新容器、日志和受控数据重置。
verify.sh校验交付包文件清单。
manifests/完整文件哈希清单和镜像 ID/平台清单。
data/唯一可变业务数据根目录；首次初始化后出现数据库、上传、反编译源码、报告和工作目录。
此目录用于“直接部署现成程序”，不含 App 源代码，也不用于证明现场修改能力。现场源代码编译验证请使用 binary-demo。

2. 服务器前置条件

  • Linux x86_64/AMD64；镜像平台固定为 linux/amd64。
  • Docker Engine 可用，且安装 Docker Compose v2（命令形式为 docker compose）。
  • 建议至少 16GB 内存；运行原生反编译时建议 24GB 或更多。
  • 准备足够磁盘空间容纳镜像、MySQL、上传二进制、反编译源码和报告。
  • 整个交付目录必须位于本地文件系统，不能让 data/ 指向符号链接。
docker version
docker compose version
uname -m

3. 先完成封存验真

在修改 .env 或启动系统之前，进入交付目录校验所有封存文件：

cd /交付路径/binary-deploy
./verify.sh package

还应将下列清单本身的 SHA-256 与用户封存时记录在交付目录之外的可信值比较：

sha256sum manifests/package.sha256
# macOS 制备机也可使用：
shasum -a 256 manifests/package.sha256
目录内的哈希清单和目录内的“根哈希文本”可以被一起替换，所以最终可信根必须由用户抄录到纸质记录、签字文件、可信 U 盘或其他独立介质。

4. 离线导入全部镜像

cd /交付路径/binary-deploy
./load-images.sh

脚本会先验证每个 *.tar.sha256，校验成功才执行 docker load。完成后可检查：

docker image ls --filter reference='binaryscan/*'
docker image inspect mysql:9.7.1

5. 配置地址和管理员账号

默认只允许从服务器本机访问 http://localhost:8080。如需在单位内网访问，应在已完成封存验真后修改 .env：

APP_BIND_IP=0.0.0.0
PUBLIC_BASE_URL=http://服务器固定内网IP:8080
APP_ALLOWED_ORIGINS=http://服务器固定内网IP:8080

首次管理员用户名和随机密码位于：

grep '^INITIAL_ADMIN_' .env
不要改动 BINARY_DATA_ROOT=./data。管理脚本只允许清理当前交付目录下经过哨兵文件确认的 data/，这是防止误删其他目录的安全边界。

6. 初始化并启动九个服务

Linux 推荐命令

cd /交付路径/binary-deploy
sudo ./manage.sh init
sudo ./manage.sh doctor
sudo ./manage.sh start

start 会使用 --pull never，不会联网获取镜像，并等待健康检查完成。成功后访问 PUBLIC_BASE_URL。

服务组成如下：

  1. mysql
  2. app
  3. scanner
  4. native-decompiler
  5. jvm-decompiler
  6. pyc-decompiler
  7. c-checker
  8. java-checker
  9. python-checker

App 外仅开放一个 HTTP 端口。数据库、worker 与 checker 均不映射宿主机端口。

7. 数据落盘位置

目录内容
data/mysql/用户、任务、finding、审计和报告索引等数据库数据。
data/storage/uploads/上传入口相关持久化内容。
data/storage/blobs/按内容寻址保存的原始二进制。
data/storage/projects/native/PE、ELF、Mach-O 等反编译生成的类 C 源码。
data/storage/projects/jvm/CLASS、JAR、DEX、APK 反编译生成的 Java 源码。
data/storage/projects/pyc/PYC 反编译生成的 Python 源码。
data/storage/artifacts/分析制品。
data/storage/reports/可下载或查看的报告文件。
data/work/scanner 与反编译 worker 的可清理工作区。

Monaco Editor 和漏洞详情通过 App 读取数据库记录所指向的 storage/projects 源码，不依赖容器临时文件系统。

8. 日常运维命令

命令行为
./manage.sh status查看九个服务状态。
./manage.sh logs -f app持续查看 App 日志；服务名可替换。
./manage.sh stop停止容器但保留容器和全部数据。
./manage.sh start启动或补齐服务，不拉取镜像。
./manage.sh restart强制重建九个容器，保留全部业务数据。
./manage.sh down移除容器与网络，保留镜像和全部业务数据。

9. 清空全部挂载数据并重新启动

不可恢复：此操作删除数据库、账号、上传文件、二进制 blob、反编译源码、漏洞结果、报告和工作目录。
cd /交付路径/binary-deploy
sudo ./manage.sh reset --yes

脚本只有同时满足以下条件才执行删除：目标严格等于当前交付包的 data/、目标不是符号链接、存在匹配当前 Compose 项目名的哨兵文件、显式提供 --yes。随后它会重建目录、检查九个镜像并重新启动。

10. 常见问题

  • 提示 required image is not loaded：先执行 ./load-images.sh。
  • 平台不匹配：目标服务器必须是 AMD64；ARM64 主机不能把本交付包当作原生生产部署使用。
  • 8080 被占用：完成封存验真后修改 APP_PORT，并同步修改公开 URL 中的端口。
  • Linux 权限失败：初始化与重置使用 sudo；不要手工把业务目录改成 0777。
  • 服务未健康：执行 ./manage.sh status 和 ./manage.sh logs 服务名。
